# Runtime and sample model

## JSON and execution

The runtime accepts the simplified `python-cdl` block JSON shape: `name`, `block_type`, typed `inputs` and `outputs`, `parameters`, optional `equations`, and composite `blocks` with `connections`. Connections may use dotted `from` / `to` or explicit `from_block` / `from_output` / `to_block` / `to_input`. Imported equations use a restricted arithmetic evaluator with variables and `min` / `max`; arbitrary Python is never evaluated. The editor palette adds known blocks and parameters but does not offer equation text editing.

Known elementary blocks include Constant, Add, Subtract, Multiply, Min, Max, MultiplyByParameter, Limiter, LimPID, PIDWithReset (PI configuration), Filter, LimRateLimiter, Hysteresis, Switch, Gain, Greater, Less, And, Or, Not, Delay, TrueDelay, Latch, UnitDelay, integer Add, BooleanToInteger, and IntegerToReal. A composite runs children in dependency order. The browser editor opens nested composites in a focused modal; users can add blocks, connections, and boundary ports there. Validation reports unsupported block types, missing endpoints, missing inputs, type mismatches, multiple drivers, equation parse errors, and cycles.

Before a building simulation starts, the runtime checks that every conventional and G36 plant, AHU, and VAV actuator command is driven by an editable CDL block rather than a raw input or an unconnected output. The conventional sample reports raw occupancy directly; G36 occupancy confirmation and preconditioning are separate required CDL outputs.

The named Python example JSON files include blocks with no equations. Their Rust implementations use the corresponding example code where available and standard control behavior otherwise. LimPID uses a clamped integral, Filter is first order, LimRateLimiter bounds change per second, and Hysteresis retains its previous Boolean output inside the deadband. Legacy standalone `VAVBoxController` JSON still has a built-in implementation for import compatibility. The default building uses a nested `VAVBoxController` composite made of elementary CDL blocks; its setpoints, PI gains, damper, reheat, airflow, and demand paths are editable. These implementations are functional interpretations of the example JSON, not a numerical port of all Python runtime code.

## Building and data

The generator in `scripts/generate_examples.py` produces a deterministic 2025 series: outdoor temperature combines annual, daily, and slower sinusoidal variations; sunlight varies by hour and season; weekday 08:00–18:00 occupancy raises internal gains. The times are UTC with no daylight-saving adjustment. The dataset is synthetic and does not represent a real weather station or building.

The separate `FourPipeG36Controls` sample is generated by `scripts/generate_g36_sample.py` from the conventional graph. It keeps the same plant, weather, ten-zone thermal model, and equipment capacities. Its VAVs use occupied heating/cooling setpoints of 21/24°C, sensor-vacant standby setpoints of 20.5/24.5°C, and off-schedule setpoints of 18/32°C. Occupancy also resets each VAV's minimum damper and airflow commands; heating calls can open the damper above minimum as PI demand rises, and the AHU fan minimum is zero. A cooling call can request damper airflow while measured supply is warm during AHU startup, so a fan and coil can establish flow instead of deadlocking on an unproven supply temperature. A six-hour lookahead guard permits learned optimal start up to three hours before the occupied schedule, while ventilation remains at the off-schedule minimum until occupancy starts. The simulator supplies the occupied schedule, time until the next occupied interval, and ten raw Brick `Occupancy_Sensor` inputs. Raw zone presence is sampled every 15 minutes using deterministic staggered arrivals, departures, and absences. Optional scenario intervals can override a zone’s raw presence sensor, including off-schedule events; overlapping intervals use the last event. These events also change the physical occupant CO₂ source, while editable CDL alone confirms presence and chooses operating modes. Editable CDL `TrueDelay` and `Latch` blocks confirm one continuous minute present and five minutes vacant. Top-level CDL blocks compare the calendar lookahead against an editable six-hour guard, then learned zone recovery times command preconditioning within a three-hour cap. Rust consumes these graph outputs and records raw and confirmed presence separately; the harness does not decide either control mode. Short delays resolve at the next internal control step. Each G36-style AHU compares outdoor and return temperatures with its supply-air target and a low-temperature limit, then enables an editable mixed-air PI loop that modulates outdoor-air fraction from the prior step’s measured mixed-air temperature. A separate minimum outside-air flow loop normalizes measured flow and the editable multizone setpoint by an editable design minimum, then uses a fan-proof-reset CDL PI to set common-damper limits. The physical outdoor and return damper actuators follow their CDL targets with a configurable full-stroke time, defaulting to 300 seconds; a stuck-position fault overrides actuator motion. Each VAV supplies gated area and population outdoor-air components, adjusted for heating or cooling air-distribution effectiveness; each AHU sums those components and measured primary flows, calculates the maximum zone outdoor-air fraction and system ventilation efficiency, and caps the corrected setpoint with editable design constants. These normalized-flow assumptions follow the OpenBuildingControl ASHRAE 62.1 multizone sequence but are not a calibrated ventilation design. A configurable mixed-volume CO₂ balance now supplies ten Brick `Zone_CO2_Level_Sensor` inputs, and editable CDL resets each occupied VAV minimum flow over a 200 ppm proportional range. The physical model supplies concentration only; the CDL graph decides airflow. Editable CDL high-limit hysteresis uses outdoor minus return temperature, while previous-step physical fan motor status provides raw fan proof; all freeze stages inhibit the economizer. Occupied mode and fan proof gate the editable minimum outside-air flow loop; normal outdoor air closes when no fan is requested but can serve cooldown or preconditioning, and an editable physical maximum caps the final command before the air-mixing model uses it. Separate G36 outdoor and return damper commands and mechanical maximums now feed an opening-ratio physical mixer. The first half of occupied minimum-air PI output opens the outdoor damper through its full stroke; the upper half independently reduces the return-damper maximum. The return command normally complements the economizer command, so the minimum-air loop can move the two dampers separately. Complete G36 2024 damper sequence validation, disable-transition delays, enthalpy options, and relief/return-fan sequences remain. The sample includes sampled pressure trim-and-respond and two timed terminal teaching alarms, but still omits the full G36 alarm and suppression sequence, a validated full demand-controlled ventilation sequence, full water-loop equipment staging and limits, and several operating modes. The occupied, unoccupied, and standby setpoints follow the [LBNL G36 thermal-zone reference](https://simulationresearch.lbl.gov/modelica/releases/v9.1.2/help/Buildings_Controls_OBC_ASHRAE_G36_ThermalZones.html).

The example graph has ten nested VAV controllers, five per AHU, two AHU controller composites, and a plant dispatch composite containing chiller, boiler, and heat-pump control blocks. Weather has 15-minute samples, held constant within each interval. The selectable maximum simulation timestep is 15 seconds, 30 seconds, 1 minute, 5 minutes, or 15 minutes. The runtime chooses an internal step that divides the selected maximum, all editable UnitDelay sample periods, and SampleTrigger periods and phase shifts. The G36 sample therefore runs at 60-second steps by default so its 120-second pressure reset receives every sample event. Sampling events requiring a step below 15 seconds are rejected for building simulation. At each simulation step, zone temperatures, outdoor weather, the prior step's measured supply-air temperature, normalized duct pressure, mixed-air temperature, delivered outdoor-air flow, terminal primary airflow, and terminal discharge temperature feed the graph. Its AHU supply-air targets, heating and cooling coil valve positions, fan speeds, outdoor-air commands, VAV outputs, and plant dispatch commands then feed the physical model. Each generated VAV has separate `airflow_request`, `damper_position`, and `airflow` outputs. The G36 `airflow` output now reports the prior step’s physical measurement, while its editable PI uses that measurement to move the damper toward the requested flow. The AHU fan uses the request, avoiding a low-pressure feedback loop in which the fan could not recover from zero flow. Older saved building graphs are migrated to add editable `airflow_request` paths; the physical model requires these graph outputs. Plant and fan requests from the prior step enter the graph to avoid an algebraic loop. Existing browser-saved building graphs are upgraded to use measured supply-air feedback while retaining user edits.

Every zone uses a one-node heat balance with 0.15 kW/K envelope conductance and 5 kWh/K thermal capacity by default. The conventional AHU graph selects 18°C supply air below 12°C outdoors, 16°C from 12–25°C, and 14°C above 25°C. The G36-style graph uses those values as an upper bound and connects VAV cooling requests to an editable two-minute trim-and-respond supply-air reset down to 14°C after a ten-minute fan-start delay. The model gives each AHU up to five normalized airflow units at full fan speed, reduced by the combined outdoor and return intake opening when their sum is below one. This is a simplified inlet-capacity constraint; changing either CDL damper command can reduce delivered airflow. Each fully open VAV passes 0.95 normalized units at unit pressure. Duct pressure is the square of fan capacity divided by the sum of damper opening areas, capped at one; delivered terminal flow is its damper opening times 0.95 times the square root of pressure. Closing one damper redistributes available air to the other terminals. The graph receives measured flow and pressure on the following step; requested flow alone does not move air. Each AHU mixes zone return air with outdoor air using its graph commands. The conventional sample provides an outdoor-air fraction; the G36 sample provides separate outdoor and return damper positions. For the latter, the physical mixer calculates the outdoor fraction as outdoor opening divided by the sum of outdoor and return openings, using zero when both are shut. The older fraction output remains a graph command alias for compatibility and inspection, while the measured fraction and outside-air flow in simulation rows come from the physical mixer. The physical model reports outside-air flow as delivered supply flow times this measured fraction. The G36-style AHU uses that feedback for an editable minimum outside-air loop and uses integer terminal requests, a connected sampled trim-and-respond graph, and a duct-pressure PI loop for pressure target reset. Its first freeze-protection stage monitors measured supply-air temperature with timed CDL thresholds, overrides outdoor air to the minimum, and sends hot-water requests that enable the plant pump and enforce a 45 °C minimum water target. A second timed CDL stage closes outdoor air and exposes a Level 3 alarm for one hour after a deeper supply-air fault. A third CDL stage latches on a raw freeze-stat trip, 15 minutes below 3.3 °C, or five minutes below 1 °C. It stops the fan, closes outside air, commands the cooling valve open and a protective heating-valve PI, requests hot- and chilled-water pumps, and exposes a Level 2 alarm. A raw operator-reset pulse clears it only after measured supply air is above 7 °C and the stat is normal. The simulator can inject these raw test inputs; alarm acknowledgment and equipment proof are not modeled. Fan-off coil metal heat transfer is outside this simplified air/water model. UnitDelay breaks the feedback cycle using its previous sampled input; the runtime supports this in both the compiled and dynamic executors. Editable CDL feedforward and PI blocks command each AHU heating and cooling valve from mixed-air and measured supply-air temperatures. The physical model converts valve position and delivered airflow to a coil request using a 20 K full-open temperature span and 8/40°C leaving-air safety bounds. Available water flow and supply temperature limit coil delivery, so actual supply-air temperature can miss the target. Source production replenishes the mixed water volume over subsequent steps. Zone sensible heat transfer uses delivered air at that actual temperature. The VAV graph already chooses occupied, standby, or unoccupied minimum airflow, so the physical model no longer applies a second off-schedule multiplier.

VAV reheat is limited by a physical 8 kW coil and a separate 40°C equipment safety cap. The G36-style graph resets the discharge target toward the zone heating setpoint plus 11 K and modulates its valve through an editable PI loop using measured discharge temperature. It also limits the command against an editable 35°C discharge target using measured primary airflow and supply temperature, and emits timed low-flow and high-discharge alarms. Heating airflow increases above its minimum only when discharge exceeds room temperature by 3 K; preconditioning can select maximum heating flow. The graph exposes each zone discharge target as a Brick point. Coil and reheat requests share available hot-water heat transfer proportionally. The plant graph adds editable hot/chilled supply-temperature proportional corrections to the previous step's predicted coil and reheat load, clamps production requests nonnegative, and splits each request using an editable CDL heat-pump dispatch constant and limiter in the plant composite. The scenario no longer supplies this control value. The physical model caps the heat pump's *combined* heating and cooling command at 80 kW by default, and the boiler and chiller at 100 kW each. These capacities can be changed in the scenario panel. Equipment energy uses heat and cooling actually produced into the water volumes, apportioned among heat pump, boiler, and chiller in the commanded proportions; source output beyond available thermal storage headroom does not consume energy. Delivered coil load and source production can differ while water temperature changes. Electricity uses heat-pump COP 3.2 heating / 3.8 cooling, chiller COP 3.5, and cubic fan power. Boiler fuel uses 90% efficiency.

Airflow and duct pressure are normalized rather than calibrated to a specific AHU and duct network. The pressure approximation has no branch losses; derived terminal airflow and discharge temperature are available as normalized/raw feedback, not calibrated field measurements. The model omits detailed equipment curves, duct and pipe losses, latent loads, and coil dynamics. In graph-commanded simultaneous mode, a teaching shared-compressor calculation now accounts for ambient heat exchange but does not resolve a refrigerant circuit or manufacturer performance map. Zone cooling and heating demand outputs are available for graph inspection; plant demand comes from calculated coil and reheat loads. These choices keep the example useful for tracing control effects but do not make it an equipment sizing or energy-compliance model.

The building simulation expects the ten named VAV composites, two AHU composites, one plant composite, and their boundary inputs/outputs. Imported standalone control examples can be tested for a single step in the editor. Each run integrates every internal simulation step and records one chart row at the end of each weather interval, keeping full-year plot data bounded to 35,040 rows. Annual energy and comfort totals use every internal step. Comfort counts time outside 20–25°C occupied or 17–29°C unoccupied, summed across zones. A 15-second full-year run executes 2,102,400 steps and can take substantially longer than the 60-second G36 default.

The simulation page compares up to 12 completed runs saved in this browser. Each run retains its control label, completion time, elapsed runtime, requested and effective timesteps, electricity, boiler fuel, and both comfort totals. All four cumulative metrics appear as labeled bars across runs, and the current-run cards use those same four Rust totals. Rust integrates them at every internal step; the browser does not re-integrate the 15-minute chart samples. Both the JSON chunk and the Worker summary serialize one shared total snapshot. The CSV and energy chart carry 15-minute mean power in kW. Multiplying each complete interval's mean by 0.25 hours reconciles with the internal-step energy total; the chart is not a separate totalizer. No bundled or cached conventional result enters the comparison. The former public `baseline_2025.json` replay artifact has been removed; manual `baseline` runs now write to a temporary file by default. Saved comparisons are snapshots from the runtime and setup used when each run completed; they are not recalculated after later changes. To compare controls fairly, rerun both graphs with the same scenario, timestep, and runtime. Person-present comfort exceedance counts time outside 20–25°C while both the schedule and raw zone presence are true; all-zone comfort-band exceedance counts every zone, including off-schedule hours outside 17–29°C, which is stricter than the G36-style 18/32°C setback.

The plant graph now owns hot/chilled loop enables, pump speed commands, and supply-water temperature setpoints. The physical model exposes supply/return temperatures and flow as raw feedback on the following step. G36 plant CDL requires both physical pump-running status and measured flow above an editable threshold before issuing heat-pump, boiler, or chiller source commands. The physical harness reports motor state from actual pump operation; the graph makes the source-proof decision. Pump speed sets quadratic pump pressure, and AHU coil and VAV reheat valve openings set an equivalent parallel-load conductance with a small bypass. Their combination determines remote differential pressure and water flow, up to 4.31 kg/s per loop at full opening and speed with the default pump curve. Measured loop flow is divided among bypass, AHU coil, and VAV reheat branches in proportion to their conductance. Bypass flow returns without delivering coil heat; each branch is limited by its own water flow, water heat capacity of 4.18 kJ/(kg·K), and a fixed 35°C hot-side or 17°C chilled-side coil return limit. The simulation records physical bypass flow, each AHU coil branch flow, and total VAV reheat branch flow as separate inspectable kg/s signals; their sums reconcile to each loop’s actual flow. Each loop has a 5,000 kg mixed water volume. The water temperature changes from source production minus delivered heat (or delivered cooling minus cooling production), and source capacities limit how quickly the volume recovers. Return temperature is calculated from delivered load divided by water flow and heat capacity; pump electricity is 3 kW per loop at full speed with a cubic speed curve. The G36 sample additionally uses each AHU cooling valve and supply-air error to issue 0–3 chilled-water reset requests, and each heating valve and supply-air deficit to issue 0–3 hot-water reset requests. Each VAV issues editable 0–3 hot-water reset requests from measured discharge-temperature deficit and its final reheat command, plus a separate valve-based plant request. Plant CDL sums the terminal and AHU reset requests, adds freeze requests, and uses terminal plant requests to enable circulation. Its plant CDL samples both five-minute trim-and-respond resets and maps them to 7–12°C chilled-water and 44–50°C hot-water targets. The conventional sample retains fixed 7/45°C targets and sizes its hot-water pump speed from an editable 90 kW branch-service design load; the earlier 180 kW stock gain starved reheat after branch flow was separated from bypass flow. The G36 graph maps the first half of each sampled plant reset into an editable remote differential-pressure setpoint and uses measured pressure in a CDL PI loop to command each pump. The loop has no pipe network, calibrated valve hydraulics, detailed physical stage-completion feedback, or calibrated actuator fault diagnostics. Editable CDL detects source-command stage changes and holds the exposed reset until measured flow and the observed stage have been stable for 900 seconds; motor-and-flow source proof is a simplified one-step interlock. Separate editable CDL pump-start diagnostics compare each graph speed command with raw motor status and time a continuous failed proof for five minutes; the diagnostics clear when motor status recovers and do not change source commands. Saved conventional and G36 graphs are migrated to the graph-owned water commands and source feedback paths while retaining existing edits.

The scenario exposes separate hot- and chilled-loop physical pump design flow, shutoff pressure, bypass conductance, coil-valve conductance, and hot-loop reheat-valve conductance. Defaults of 4.31 kg/s and 80 kPa per loop preserve the previous equivalent hydraulic curve. Changing these physical values alters measured flow and remote differential pressure at the same CDL pump command; these measurements return to the graph on the next step, where editable CDL determines pump speed and source proof. These parameters allow sensitivity studies but do not calibrate the model to a real pipe or valve network.

Timed hot- or chilled-water pump faults stop only the selected physical motor. The CDL speed command remains available for inspection, while measured loop flow and pressure drop to zero and the failed motor draws no pump electricity. The graph receives those measurements on the next step and its editable source-proof blocks decide whether source commands remain enabled. The fault schedule never assigns a source-proof or alarm value.

## Brick point metadata

The bundled graph's inputs and outputs include `label`, `unit`, and `brick_class` metadata. The class is a local name from [Brick 1.5](https://github.com/BrickSchema/Brick/releases/tag/v1.5.0), such as `Zone_Air_Temperature_Sensor`, `Occupancy_Sensor`, `Supply_Air_Temperature_Setpoint`, or `Damper_Position_Command`. Modeled calculations such as normalized airflow request use generic `brick:Point` and are not described as physical sensors. Connector `name` values remain stable graph identifiers so saved edges and traces continue to work. Older browser-saved copies of the bundled graph receive missing metadata when loaded. CXF export retains display labels, Brick classes, and non-CXF units in `ace:` extension properties so an import round-trip preserves the sensor classification. This is point classification, not a full Brick RDF model of equipment, locations, and relationships.

## Browser interface

The Web Worker initializes the Wasm module and accepts `validate`, `execute`, `simulate`, and `cancel` messages. The Rust interface exposes `validate_json(graph_json)`, `execute_json(graph_json, inputs_json, dt_seconds)`, and a `Simulation` object with `set_traces(targets_json)`, `step_chunk_arrow(count)`, progress, total, completion, and summary accessors. The older JSON `step_chunk(count)` remains available for baseline generation and Rust tests. Recorded results cross the Wasm/worker/Vue boundary as Apache Arrow IPC batches with typed numeric columns, transferred as binary buffers. Vue keeps these batches as Arrow tables and materializes only chart samples, the latest row, or explicitly exported CSV rows. Selected graph signals become named Arrow columns and are collected only at recording boundaries. Annual integration and control graph execution still run entirely in Rust. At simulation construction, the editable building graph is compiled to indexed numeric slots, flat instructions, cached parameters, and pre-resolved trace locations. Per-step evaluation uses those slots. Graphs with equation or legacy leaves use the original dynamic executor for compatibility. Arrow stores and transfers recorded time-series results; it does not execute the control graph. Physical process variables and graph signals can be selected together; the browser groups series by units and provides a labeled y-axis for each group. Graph signal units use declared connector metadata where available and known example port names otherwise; unknown units are labeled "unit not declared." The worker yields between chunks to process cancellation.

Rust accumulates the four yearly summary totals once per physical step. Electricity and boiler fuel integrate equipment power over the step; the 15-minute chart power samples are interval means of those same increments. All-zone comfort counts each zone outside its scheduled 20–25°C or off-hours 17–29°C band. Present-zone comfort is a subset: it counts only raw presence during scheduled occupancy outside 20–25°C. The worker forwards these totals without recalculation. The current-run tiles and comparison bars use the same summary fields; completed comparison runs are browser-saved snapshots and are not updated when controls, assumptions, or the runtime change.

The four-pipe heat pump uses a scenario-editable, synthetic outdoor-temperature performance table. Rust interpolates outdoor-conditioned thermal capacity and heating/cooling COP. Separate hot- and chilled-water tables multiply each service's physical capacity and COP using measured supply temperature at the start of the step. The shared total limit is the larger of the two service capacities, so favorable water conditions can raise a single service above its outdoor-only baseline. Rust passes the shared and service-specific capacities into the G36 plant graph as raw measurements, and that graph alone allocates heat-pump service and boiler/chiller residual commands with editable Min blocks. Rust applies the same capacities as physical delivery limits, without selecting source commands. Values beyond table endpoints hold the nearest point. The capacity and COP multipliers default to one, preserving earlier behavior. An editable physical curve also multiplies heating and cooling COP at the actual delivered heat-pump part-load fraction. These factorized corrections are synthetic until fitted to equipment data; defrost and a calibrated joint manufacturer capacity/efficiency map are not modeled.

The simultaneous-service physical model has a scenario-editable compressor savings fraction. At zero, heating and cooling use independent compressor electricity; at one, the smaller separate-service compressor load is avoided, preserving the original teaching model. Intermediate values interpolate only the compressor work and ambient heat exchange. The CDL mode and thermal dispatch are unchanged. This scalar is not a calibrated manufacturer map.

Scenario equipment-outage windows provide raw heat-pump, boiler, and chiller availability statuses. The G36 CDL plant graph gates source commands from those Brick `Status` inputs and redispatches eligible load; Rust limits physical output from unavailable equipment. Both bundled plant graphs now publish separate editable CDL `plant_heat_pump_start_command`, `plant_boiler_start_command`, and `plant_chiller_start_command` outputs. Rust starts each physical source only from that Boolean request plus raw equipment availability and startup/failure physics; it no longer infers a start decision from positive thermal kW. The physical model returns running status after the scenario startup delay, and G36 CDL uses it to qualify water-reset stage holds. Hot-water plant status is true when the boiler runs or the heat pump runs in a heating-capable CDL mode, independent of instantaneous thermal delivery. The G36 graph uses editable five-minute `TrueDelay` qualification of continuous residual boiler and chiller load before backup starts, followed by five-minute `TrueFalseHold` minimum-on periods on all three start commands and a demand-driven minimum-off period on the heat pump; boiler and chiller off time is enforced after actual running proof falls, leaving their stage-up delay independently editable. Raw unavailability and a latched CDL start fault override the on hold immediately. A separate CDL `FallingEdge` on raw physical running proof starts an editable five-minute restart lockout after a source stops, including an outage or fault stop. For the heat pump, this can extend the demand-driven off period when the physical stop occurs later than the demand transition. Each failed-start timer samples the final issued CDL start command rather than thermal demand, so intentional off lockout cannot be mistaken for a failed start. These are equipment-specific teaching settings, not verified 2024 G36 durations. A CDL start command can keep a source physically running while its compatible thermal command is zero; this teaching model does not charge idle source power. This is synthetic running proof, not a manufacturer stage-complete or fault-code measurement. The conventional graph retains its existing control logic and can lose physical source output during an outage without graph-based redispatch.
