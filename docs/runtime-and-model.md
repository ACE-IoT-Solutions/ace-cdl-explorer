# Runtime and sample model

## JSON and execution

The runtime accepts the simplified `python-cdl` block JSON shape: `name`, `block_type`, typed `inputs` and `outputs`, `parameters`, optional `equations`, and composite `blocks` with `connections`. Connections may use dotted `from` / `to` or explicit `from_block` / `from_output` / `to_block` / `to_input`. Imported equations use a restricted arithmetic evaluator with variables and `min` / `max`; arbitrary Python is never evaluated. The editor palette adds known blocks and parameters but does not offer equation text editing.

Known elementary blocks include Constant, Add, Subtract, Multiply, Min, MultiplyByParameter, Limiter, LimPID, Filter, LimRateLimiter, Hysteresis, Switch, Gain, Greater, Less, And, Or, Not, and Delay. A composite runs children in dependency order. The browser editor opens nested composites in a focused modal; users can add blocks, connections, and boundary ports there. Validation reports unsupported block types, missing endpoints, missing inputs, type mismatches, multiple drivers, equation parse errors, and cycles.

The named Python example JSON files include blocks with no equations. Their Rust implementations use the corresponding example code where available and standard control behavior otherwise. LimPID uses a clamped integral, Filter is first order, LimRateLimiter bounds change per second, and Hysteresis retains its previous Boolean output inside the deadband. Legacy standalone `VAVBoxController` JSON still has a built-in implementation for import compatibility. The default building uses a nested `VAVBoxController` composite made of elementary CDL blocks; its setpoints, PI gains, damper, reheat, airflow, and demand paths are editable. These implementations are functional interpretations of the example JSON, not a numerical port of all Python runtime code.

## Building and data

The generator in `scripts/generate_examples.py` produces a deterministic 2025 series: outdoor temperature combines annual, daily, and slower sinusoidal variations; sunlight varies by hour and season; weekday 08:00–18:00 occupancy raises internal gains. The times are UTC with no daylight-saving adjustment. The dataset is synthetic and does not represent a real weather station or building.

The separate `FourPipeG36Controls` sample is generated by `scripts/generate_g36_sample.py` from the conventional graph. It keeps the same plant, weather, ten-zone thermal model, and equipment capacities. Its VAVs use occupied heating/cooling setpoints of 21/24°C, sensor-vacant standby setpoints of 20.5/24.5°C, and off-schedule setpoints of 16/32°C. Occupancy also resets each VAV's minimum damper and airflow commands; heating calls retain a minimum discharge path, and the AHU fan minimum is zero. A four-hour preconditioning window requests occupied temperature setpoints before the occupied schedule, while ventilation remains at the off-schedule minimum until occupancy starts. The simulator supplies synthetic `schedule_occupied` and `preconditioning_mode` Booleans plus ten Brick `Occupancy_Sensor` Booleans. Raw zone presence is sampled every 15 minutes using deterministic staggered arrivals, departures, and absences; the Rust runtime confirms five continuous minutes vacant or one continuous minute present before changing each sensor input. These inputs and their 0/1 histories can be plotted and exported. The G36 sample covers these occupancy-related sequences only; it does not model full Guideline 36 AHU trim-and-respond, economizer, demand-controlled ventilation, alarms, or all operating modes. The occupied, unoccupied, and standby setpoints follow the [LBNL G36 thermal-zone reference](https://simulationresearch.lbl.gov/modelica/releases/v9.1.2/help/Buildings_Controls_OBC_ASHRAE_G36_ThermalZones.html).

The example graph has ten nested VAV controllers, five per AHU, two AHU controller composites, and a plant dispatch composite containing chiller, boiler, and heat-pump control blocks. Weather has 15-minute samples, held constant within each interval. The selectable simulation timestep is 15 seconds, 30 seconds, 1 minute, 5 minutes, or 15 minutes. At each simulation step, zone temperatures, outdoor weather, and the prior step's measured supply-air temperature feed the graph. Its AHU supply-air targets, fan speeds, VAV outputs, and plant dispatch commands then feed the physical model. Plant and fan requests from the prior step enter the graph to avoid an algebraic loop. Existing browser-saved building graphs are upgraded to use measured supply-air feedback while retaining user edits.

Every zone uses a one-node heat balance with 0.15 kW/K envelope conductance and 5 kWh/K thermal capacity by default. The default AHU graph resets supply air to 18°C below 12°C outdoors, 16°C from 12–25°C, and 14°C above 25°C. The model gives each AHU up to five normalized airflow units at full fan speed. When VAVs request more, available air is shared proportionally. Each AHU mixes 80% zone return air with 20% outdoor air. Heating and cooling coil requests are calculated from this mixed-air temperature, delivered airflow, and the AHU supply-air target. Plant output limits coil delivery, so actual supply-air temperature can miss the target. Zone sensible heat transfer uses delivered air at that actual temperature.

VAV reheat is limited to 8 kW per zone and a 40°C discharge-air target, so reduced airflow can also limit heating. Coil and reheat requests share available plant heating proportionally. The default plant dispatch splits the previous step's load using the configurable heat-pump fraction. Equipment energy uses heat and cooling actually delivered, apportioned among heat pump, boiler, and chiller in the commanded proportions; excess plant command does not consume energy. Electricity uses heat-pump COP 3.2 heating / 3.8 cooling, chiller COP 3.5, and cubic fan power. Boiler fuel uses 90% efficiency.

Airflow is normalized rather than calibrated to a specific AHU size, and duct pressure is held at its nominal value in the VAV control graph. The model omits equipment nameplate limits, duct and pipe losses, latent loads, coil dynamics, and heat-pump heat recovery between simultaneous heating and cooling. Zone cooling and heating demand outputs are available for graph inspection; plant demand comes from calculated coil and reheat loads. These choices keep the example useful for tracing control effects but do not make it an equipment sizing or energy-compliance model.

The building simulation expects the ten named VAV composites, two AHU composites, one plant composite, and their boundary inputs/outputs. Imported standalone control examples can be tested for a single step in the editor. Baseline values were calculated from the default graph and assumptions at 15-minute steps, then sampled hourly for the chart. Custom runs integrate every selected simulation step and record one chart row at the end of each weather interval, keeping full-year plot data bounded to 35,040 rows. Annual energy and comfort totals use every simulation step. Comfort counts time outside 20–25°C occupied or 17–29°C unoccupied, summed across zones. A 15-second full-year run executes 2,102,400 steps and can take substantially longer than the default.

The simulation page compares a completed G36-style run with the bundled conventional annual summary when scenario assumptions are at their defaults. Both use the same synthetic weather and physical model. The comparison uses occupied comfort exceedance (outside 20–25°C while the schedule is occupied); the general unmet-comfort metric also counts off-schedule hours outside 17–29°C, which is stricter than the G36-style 16/32°C setback. With edited building assumptions, run both controls explicitly for a fair comparison; the bundled baseline is labeled as using defaults.

## Brick point metadata

The bundled graph's inputs and outputs include `label`, `unit`, and `brick_class` metadata. The class is a local name from [Brick 1.5](https://github.com/BrickSchema/Brick/releases/tag/v1.5.0), such as `Zone_Air_Temperature_Sensor`, `Occupancy_Sensor`, `Supply_Air_Temperature_Setpoint`, or `Damper_Position_Command`. Modeled calculations such as normalized airflow request use generic `brick:Point` and are not described as physical sensors. Connector `name` values remain stable graph identifiers so saved edges and traces continue to work. Older browser-saved copies of the bundled graph receive missing metadata when loaded. CXF export retains display labels, Brick classes, and non-CXF units in `ace:` extension properties so an import round-trip preserves the sensor classification. This is point classification, not a full Brick RDF model of equipment, locations, and relationships.

## Browser interface

The Web Worker initializes the Wasm module and accepts `validate`, `execute`, `simulate`, and `cancel` messages. The Rust interface exposes `validate_json(graph_json)`, `execute_json(graph_json, inputs_json, dt_seconds)`, and a `Simulation` object with `set_traces(targets_json)`, `step_chunk_arrow(count)`, progress, total, completion, and summary accessors. The older JSON `step_chunk(count)` remains available for baseline generation and Rust tests. Recorded results cross the Wasm/worker/Vue boundary as Apache Arrow IPC batches with typed numeric columns, transferred as binary buffers. Vue keeps these batches as Arrow tables and materializes only chart samples, the latest row, or explicitly exported CSV rows. Selected graph signals become named Arrow columns and are collected only at recording boundaries. Annual integration and control graph execution still run entirely in Rust. At simulation construction, the editable building graph is compiled to indexed numeric slots, flat instructions, cached parameters, and pre-resolved trace locations. Per-step evaluation uses those slots. Graphs with equation or legacy leaves use the original dynamic executor for compatibility. Arrow stores and transfers recorded time-series results; it does not execute the control graph. Physical process variables and graph signals can be selected together; the browser groups series by units and provides a labeled y-axis for each group. Graph signal units use declared connector metadata where available and known example port names otherwise; unknown units are labeled "unit not declared." The worker yields between chunks to process cancellation.
