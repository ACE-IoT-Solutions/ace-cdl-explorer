# Runtime and sample model

## JSON and execution

The runtime accepts the simplified `python-cdl` block JSON shape: `name`, `block_type`, typed `inputs` and `outputs`, `parameters`, optional `equations`, and composite `blocks` with `connections`. Connections may use dotted `from` / `to` or explicit `from_block` / `from_output` / `to_block` / `to_input`. Imported equations use a restricted arithmetic evaluator with variables and `min` / `max`; arbitrary Python is never evaluated. The editor palette adds known blocks and parameters but does not offer equation text editing.

Known elementary blocks include Constant, Add, Subtract, Multiply, Min, Max, MultiplyByParameter, Limiter, LimPID, Filter, LimRateLimiter, Hysteresis, Switch, Gain, Greater, Less, And, Or, Not, Delay, TrueDelay, Latch, UnitDelay, integer Add, BooleanToInteger, and IntegerToReal. A composite runs children in dependency order. The browser editor opens nested composites in a focused modal; users can add blocks, connections, and boundary ports there. Validation reports unsupported block types, missing endpoints, missing inputs, type mismatches, multiple drivers, equation parse errors, and cycles.

The named Python example JSON files include blocks with no equations. Their Rust implementations use the corresponding example code where available and standard control behavior otherwise. LimPID uses a clamped integral, Filter is first order, LimRateLimiter bounds change per second, and Hysteresis retains its previous Boolean output inside the deadband. Legacy standalone `VAVBoxController` JSON still has a built-in implementation for import compatibility. The default building uses a nested `VAVBoxController` composite made of elementary CDL blocks; its setpoints, PI gains, damper, reheat, airflow, and demand paths are editable. These implementations are functional interpretations of the example JSON, not a numerical port of all Python runtime code.

## Building and data

The generator in `scripts/generate_examples.py` produces a deterministic 2025 series: outdoor temperature combines annual, daily, and slower sinusoidal variations; sunlight varies by hour and season; weekday 08:00–18:00 occupancy raises internal gains. The times are UTC with no daylight-saving adjustment. The dataset is synthetic and does not represent a real weather station or building.

The separate `FourPipeG36Controls` sample is generated by `scripts/generate_g36_sample.py` from the conventional graph. It keeps the same plant, weather, ten-zone thermal model, and equipment capacities. Its VAVs use occupied heating/cooling setpoints of 21/24°C, sensor-vacant standby setpoints of 20.5/24.5°C, and off-schedule setpoints of 16/32°C. Occupancy also resets each VAV's minimum damper and airflow commands; heating calls can open the damper above minimum as PI demand rises, and the AHU fan minimum is zero. A six-hour preconditioning window requests occupied temperature setpoints before the occupied schedule, while ventilation remains at the off-schedule minimum until occupancy starts. The simulator supplies the occupied schedule, time until the next occupied interval, and ten raw Brick `Occupancy_Sensor` inputs. Raw zone presence is sampled every 15 minutes using deterministic staggered arrivals, departures, and absences. Editable CDL `TrueDelay` and `Latch` blocks confirm one continuous minute present and five minutes vacant. Top-level CDL blocks compare the calendar lookahead against an editable six-hour horizon to command preconditioning. Rust consumes these graph outputs and records raw and confirmed presence separately; the harness does not decide either control mode. Short delays resolve at the next internal control step. Each G36-style AHU compares outdoor and return temperatures with its supply-air target and a low-temperature limit, then enables an editable mixed-air PI loop that modulates outdoor-air fraction from the prior step’s measured mixed-air temperature. A separate minimum outside-air flow loop can raise that command. This omits the full G36 economizer enable, damper limits, relief/return-fan, and freeze-protection sequences. The sample includes sampled pressure trim-and-respond and two timed terminal teaching alarms, but still omits the full G36 alarm and suppression sequence, demand-controlled ventilation, full water-loop pressure/temperature reset and staging, and several operating modes. The occupied, unoccupied, and standby setpoints follow the [LBNL G36 thermal-zone reference](https://simulationresearch.lbl.gov/modelica/releases/v9.1.2/help/Buildings_Controls_OBC_ASHRAE_G36_ThermalZones.html).

The example graph has ten nested VAV controllers, five per AHU, two AHU controller composites, and a plant dispatch composite containing chiller, boiler, and heat-pump control blocks. Weather has 15-minute samples, held constant within each interval. The selectable maximum simulation timestep is 15 seconds, 30 seconds, 1 minute, 5 minutes, or 15 minutes. The runtime chooses an internal step that divides both the selected maximum and all editable UnitDelay sample periods. The G36 sample therefore runs at 60-second steps by default so its 120-second pressure reset receives every sample event. Sample periods requiring a step below 15 seconds are rejected for building simulation. At each simulation step, zone temperatures, outdoor weather, the prior step's measured supply-air temperature, normalized duct pressure, mixed-air temperature, delivered outdoor-air flow, terminal primary airflow, and terminal discharge temperature feed the graph. Its AHU supply-air targets, heating and cooling coil valve positions, fan speeds, outdoor-air commands, VAV outputs, and plant dispatch commands then feed the physical model. Each generated VAV now has separate `airflow_request` and pressure-affected `airflow` estimate outputs. The fan uses the former; using the latter created a low-pressure feedback loop in which the fan could not recover from zero flow. Older saved building graphs are migrated to add editable `airflow_request` paths; the physical model requires these graph outputs. Plant and fan requests from the prior step enter the graph to avoid an algebraic loop. Existing browser-saved building graphs are upgraded to use measured supply-air feedback while retaining user edits.

Every zone uses a one-node heat balance with 0.15 kW/K envelope conductance and 5 kWh/K thermal capacity by default. The default AHU graph resets supply air to 18°C below 12°C outdoors, 16°C from 12–25°C, and 14°C above 25°C. The model gives each AHU up to five normalized airflow units at full fan speed. When VAVs request more, available air is shared proportionally. Normalized duct pressure follows the square of available fan capacity divided by VAV request, capped at one, and feeds the VAV graph on the following step. Each AHU mixes zone return air with outdoor air using its graph's outdoor-air fraction output; both sample graphs provide this required command. The physical model reports outside-air flow as delivered supply flow times this fraction. The G36-style AHU uses that feedback for an editable minimum outside-air loop and uses integer terminal requests, a connected sampled trim-and-respond graph, and a duct-pressure PI loop for pressure target reset. UnitDelay breaks the feedback cycle using its previous sampled input; the runtime supports this in both the compiled and dynamic executors. Editable CDL feedforward and PI blocks command each AHU heating and cooling valve from mixed-air and measured supply-air temperatures. The physical model converts valve position and delivered airflow to a coil request using a 20 K full-open temperature span and 8/40°C leaving-air safety bounds. Plant output limits coil delivery, so actual supply-air temperature can miss the target. Zone sensible heat transfer uses delivered air at that actual temperature. The VAV graph already chooses occupied, standby, or unoccupied minimum airflow, so the physical model no longer applies a second off-schedule multiplier.

VAV reheat is limited by a physical 8 kW coil and a separate 40°C equipment safety cap. The G36-style graph further limits its valve command against an editable 35°C discharge target using measured primary airflow and supply temperature, and emits timed low-flow and high-discharge alarms. Coil and reheat requests share available plant heating proportionally. The default plant dispatch splits the previous step's load using the configurable heat-pump fraction. The physical model caps the heat pump's *combined* heating and cooling command at 80 kW by default, and the boiler and chiller at 100 kW each. These capacities can be changed in the scenario panel. Equipment energy uses heat and cooling actually delivered, apportioned among heat pump, boiler, and chiller in the commanded proportions; excess plant command does not consume energy. Electricity uses heat-pump COP 3.2 heating / 3.8 cooling, chiller COP 3.5, and cubic fan power. Boiler fuel uses 90% efficiency.

Airflow and duct pressure are normalized rather than calibrated to a specific AHU and duct network. The pressure approximation has no branch losses; derived terminal airflow and discharge temperature are available as normalized/raw feedback, not calibrated field measurements. The model omits detailed equipment curves, duct and pipe losses, latent loads, coil dynamics, and heat-pump heat recovery between simultaneous heating and cooling. Zone cooling and heating demand outputs are available for graph inspection; plant demand comes from calculated coil and reheat loads. These choices keep the example useful for tracing control effects but do not make it an equipment sizing or energy-compliance model.

The building simulation expects the ten named VAV composites, two AHU composites, one plant composite, and their boundary inputs/outputs. Imported standalone control examples can be tested for a single step in the editor. The bundled conventional chart baseline was calculated at 15-minute steps, then sampled hourly. Custom runs integrate every internal simulation step and record one chart row at the end of each weather interval, keeping full-year plot data bounded to 35,040 rows. Annual energy and comfort totals use every internal step. Comfort counts time outside 20–25°C occupied or 17–29°C unoccupied, summed across zones. A 15-second full-year run executes 2,102,400 steps and can take substantially longer than the 60-second G36 default.

The simulation page compares a completed G36-style run with the bundled conventional annual summary when scenario assumptions are at their defaults. Both use the same synthetic weather and physical model. The comparison uses a separate conventional annual summary calculated at the G36 sample's 60-second internal step, rather than the 15-minute conventional chart baseline. It uses person-present comfort exceedance (outside 20–25°C while both the schedule and raw zone presence are true); the general unmet-comfort metric also counts off-schedule hours outside 17–29°C, which is stricter than the G36-style 16/32°C setback. With edited building assumptions, run both controls explicitly for a fair comparison; the bundled baseline is labeled as using defaults.

The plant graph now owns hot/chilled loop enables, pump speed commands, and supply-water temperature setpoints. The physical model exposes supply/return temperatures and flow as raw feedback on the following step. Pump speed sets flow up to 4.31 kg/s per loop. Sensible heat transfer is limited by that flow, water heat capacity of 4.18 kJ/(kg·K), and a fixed 35°C hot-side or 17°C chilled-side coil return limit. The plant source capacity remains a separate limit. Return temperature is calculated from delivered load divided by water flow and heat capacity; pump electricity is 3 kW per loop at full speed with a cubic speed curve. The G36 sample additionally uses each AHU cooling valve and supply-air temperature error to issue 0–3 chilled-water reset requests. Its plant CDL samples a five-minute trim-and-respond reset and maps it to a 7–12°C chilled-water target. The conventional sample retains a fixed 7°C target. The loop has no pipe or mixing volume, hydraulic pressure network, plant staging hold, hot-water reset, or pump proof. Saved conventional and G36 graphs are migrated to the new graph-owned water commands while retaining existing edits.

## Brick point metadata

The bundled graph's inputs and outputs include `label`, `unit`, and `brick_class` metadata. The class is a local name from [Brick 1.5](https://github.com/BrickSchema/Brick/releases/tag/v1.5.0), such as `Zone_Air_Temperature_Sensor`, `Occupancy_Sensor`, `Supply_Air_Temperature_Setpoint`, or `Damper_Position_Command`. Modeled calculations such as normalized airflow request use generic `brick:Point` and are not described as physical sensors. Connector `name` values remain stable graph identifiers so saved edges and traces continue to work. Older browser-saved copies of the bundled graph receive missing metadata when loaded. CXF export retains display labels, Brick classes, and non-CXF units in `ace:` extension properties so an import round-trip preserves the sensor classification. This is point classification, not a full Brick RDF model of equipment, locations, and relationships.

## Browser interface

The Web Worker initializes the Wasm module and accepts `validate`, `execute`, `simulate`, and `cancel` messages. The Rust interface exposes `validate_json(graph_json)`, `execute_json(graph_json, inputs_json, dt_seconds)`, and a `Simulation` object with `set_traces(targets_json)`, `step_chunk_arrow(count)`, progress, total, completion, and summary accessors. The older JSON `step_chunk(count)` remains available for baseline generation and Rust tests. Recorded results cross the Wasm/worker/Vue boundary as Apache Arrow IPC batches with typed numeric columns, transferred as binary buffers. Vue keeps these batches as Arrow tables and materializes only chart samples, the latest row, or explicitly exported CSV rows. Selected graph signals become named Arrow columns and are collected only at recording boundaries. Annual integration and control graph execution still run entirely in Rust. At simulation construction, the editable building graph is compiled to indexed numeric slots, flat instructions, cached parameters, and pre-resolved trace locations. Per-step evaluation uses those slots. Graphs with equation or legacy leaves use the original dynamic executor for compatibility. Arrow stores and transfers recorded time-series results; it does not execute the control graph. Physical process variables and graph signals can be selected together; the browser groups series by units and provides a labeled y-axis for each group. Graph signal units use declared connector metadata where available and known example port names otherwise; unknown units are labeled "unit not declared." The worker yields between chunks to process cancellation.
