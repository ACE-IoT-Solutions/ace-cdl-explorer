# OBC control-sequence verification

Run `python -m pip install -r verification/requirements.txt`, then `python scripts/verify-obc.py` from the repository root. The command replays each archived input trend through both the Rust compatibility `Executor` and the compiled executor used by the browser, writes both observed output trends, and uses LBNL's [pyfunnel](https://github.com/lbl-srg/funnel) to compare each with the reference output at the declared time and value tolerances. A nonzero funnel excess in either path fails CI. The `verification/results/` directory contains each actual trace, funnel bounds, errors, and a summary.

Most reference CSV values were independently calculated from the equations in the [Modelica Buildings CDL blocks](https://github.com/lbl-srg/modelica-buildings/tree/d3d8e6f76514dfbc7d65574c6b5a777b686fe1b7/Buildings/Controls/OBC/CDL), pinned to commit `d3d8e6f76514dfbc7d65574c6b5a777b686fe1b7`. The SampleTrigger period and shifted-period traces are calculated from the pinned `y = sample(t0, period)` source equation with the same 0.5-second period and 1.3-second shift as the official validation model. A discrete runtime reports a one-step pulse at the first step that reaches each event; these fixtures land exactly on the sample times. The BooleanToReal trace contains the 101 input/output samples from the pinned [Dymola validation result](https://github.com/lbl-srg/modelica-buildings/blob/d3d8e6f76514dfbc7d65574c6b5a777b686fe1b7/Buildings/Resources/ReferenceResults/Dymola/Buildings_Controls_OBC_CDL_Conversions_Validation_BooleanToReal.txt), sampled over four seconds. The three TrueFalseHold traces are the 101-point `truFalHol`, `truFalHol1`, and `truFalHol4` input and output series from the pinned [Dymola validation result](https://github.com/lbl-srg/modelica-buildings/blob/d3d8e6f76514dfbc7d65574c6b5a777b686fe1b7/Buildings/Resources/ReferenceResults/Dymola/Buildings_Controls_OBC_CDL_Logical_Validation_TrueFalseHold.txt), sampled every 72 seconds. Their 72-second time tolerance accounts for input events between those samples; no Boolean value error is permitted outside that time window. The editable G36 zone-status composite uses four output series for both window-sensor variants from the pinned [Dymola ZoneStatus validation result](https://github.com/lbl-srg/modelica-buildings/blob/d3d8e6f76514dfbc7d65574c6b5a777b686fe1b7/Buildings/Resources/ReferenceResults/Dymola/Buildings_Controls_OBC_ASHRAE_G36_ZoneGroups_Validation_ZoneStatus.txt). The archived result is `g36_zone_status_dymola.txt`; `python scripts/generate_zone_status_reference.py` extracts the eight 101-sample CSVs, and the verification command checks them for drift. The four recorded outputs match with zero time or value tolerance in both Rust executors, both in the standalone example and in a `zone_status_1` instance extracted from the bundled G36 graph. The latter cases use the same archived traces with `input_offsets` of −273.15 K on the five temperature inputs to exercise the building’s °C-valued ports; the source differences and Boolean decisions must remain identical. The `source` field in `suite.json` identifies the source for each case. These values are checked into the repository; the verification run does not generate its own expected outputs. The P controller/limiter case uses the checked-in graph and the official MultiplyByParameter and Min equations.

The zone-recovery case extracts `zone_group_1/optimal_warmup_1_learner` directly from the bundled G36 graph. Its 60-second, four-day input trend contains three measured recovery episodes and a day when no start is needed. The expected rate follows the [pinned OBC OptimalStartCalculation slope, moving-mean, and floor equations](https://github.com/lbl-srg/modelica-buildings/blob/d3d8e6f76514dfbc7d65574c6b5a777b686fe1b7/Buildings/Controls/OBC/Utilities/BaseClasses/OptimalStartCalculation.mo): captured 3 K error divided by at least 120 seconds of recovery, the initial zero sample and last three daily samples, and a 1/3600 K/s minimum. `python scripts/generate_optimal_start_reference.py` regenerates the checked-in trend; the verification command checks it for drift. This tests the learner's bounded slope path under completed recoveries. It is a source-equation trace, not an independent Modelica run of the full optimal-start or zone-group composite.

Each CSV has `time_s`, one column per graph input, and `y` for the selected reference output. A case may name an `output` other than `y`, as for the Timer's `passed` connector. Values use CDL units; Boolean values are `0` and `1`. The configured tolerances are absolute. Timestamps must increase, and inputs and parameters remain the same for the Rust and reference series. This follows the [OBC time-series verification method](https://obc.lbl.gov/specification/verification.html) for control logic; it does not test physical point wiring or building performance.

Current coverage is BooleanToReal, Add, MultiplyByParameter, Limiter, Hysteresis, Switch, TrueDelay, TrueFalseHold, Latch, UnitDelay, TriggeredSampler, TriggeredMovingMean, SampleTrigger, Edge, FallingEdge, Timer, and three composite graphs. It caught and corrected the Rust hysteresis polarity and the standard Switch connector order. The fixture set is a small subset of CDL. The pinned ZoneStatus result records four of the composite's eight outputs; the other four outputs still need independent reference traces. Modelica-generated traces for the complete optimal-start sequence, PID, Filter, and rate limiters remain next steps, as does unit conversion for BAS trends in non-SI units. Verification of the ten-zone building's plant and thermal model would need an independent system reference in addition to these control-logic traces.
